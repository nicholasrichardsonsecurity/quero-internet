# Missão 1.7 — Painel Operacional MVP

## Estado

INICIADA

## Objetivo

Criar a primeira visão operacional utilizável para prefeitura e provedor acompanharem o ciclo ponta a ponta do programa de conectividade:

`solicitação → elegibilidade → encaminhamento → viabilidade → instalação → ativação → serviço ativo`

A missão não deve criar novas decisões automáticas, não deve expor dados sensíveis além do necessário e não deve substituir integração IXC/SGP real.

## Resultado esperado

Entregar um painel mínimo, seguro e rastreável para operação diária, começando por leitura e navegação:

- resumo de indicadores por contexto organizacional;
- lista operacional de solicitações/encaminhamentos;
- filtros por status e programa;
- visão municipal minimizada;
- visão do provedor com dados operacionais próprios;
- links/rotas para acompanhar instalação e serviço;
- sem exposição de CPF/documento bruto;
- sem exposição de referência externa/técnica do provedor para município.

## Escopo técnico inicial

### Backend

Criar endpoint de leitura operacional, sem mutação:

- `GET /operations/overview`

O endpoint deve derivar o escopo a partir da sessão autenticada:

- município vê apenas dados de seu contexto municipal;
- provedor vê apenas dados atribuídos ao seu contexto de provedor;
- superadmin/owner/admin respeitam o contexto ativo da organização;
- sem tenant por header;
- deny-by-default.

Dados mínimos do overview:

- contadores por etapa/status;
- itens recentes com IDs técnicos internos necessários para navegação;
- programa vinculado;
- datas relevantes;
- status da aplicação, encaminhamento, viabilidade, instalação e serviço;
- DTO diferente para município e provedor.

### Frontend

Criar primeira tela web autenticada:

- rota operacional, preferencialmente `/dashboard/operations` ou equivalente existente;
- cards de indicadores;
- tabela/lista responsiva;
- estados vazios e loading/error;
- design compatível com o padrão govtech já usado no projeto;
- sem depender de dados mockados fixos quando existir BFF/API possível.

### BFF / Web

Se o web app já usa BFF por cookie HttpOnly, criar rota BFF segura para chamar a API:

- preservar cookie/sessão;
- não expor token no cliente;
- tratar erro genérico sem vazar stack.

## Regras permanentes

1. O painel é leitura operacional, não mecanismo de decisão.
2. Nenhum dado sensível de documento deve ser exibido.
3. Município não vê `externalServiceReference`, motivo técnico livre do provedor, portas, OLT, PON, CTO ou qualquer referência interna de rede.
4. Provedor vê apenas operações atribuídas a ele e ao tenant autorizado.
5. O status exibido deve refletir dados persistidos, não inferência de CEP ou heurística.
6. Não criar integração IXC/SGP nesta missão.
7. Não criar telemetria automática nesta missão.
8. Todos os endpoints devem seguir autorização deny-by-default.
9. O painel deve ser útil mesmo com poucos dados e seguro quando vazio.
10. CI e Security Gate devem passar antes de PR/merge.

## Fora do escopo

- CRUD completo de beneficiários.
- Upload/download de evidências.
- Integração real IXC/SGP.
- Webhooks externos.
- Notificações.
- BI avançado.
- Gráficos complexos.
- Exportação CSV/PDF.
- edição operacional pela interface.

## Critérios de aceitação

- Backend com endpoint operacional autenticado.
- Escopo municipal/provedor testado ou coberto por regras explícitas.
- DTO municipal minimizado.
- Frontend com cards e lista operacional responsiva.
- Sem CPF/documento bruto no payload.
- Sem referência técnica do provedor no DTO municipal.
- Typecheck, testes, build e migrations continuam verdes.
- Security Gate verde.
