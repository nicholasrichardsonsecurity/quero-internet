# Missão 1.8 — Dashboard operacional real

## Objetivo

Transformar a tela inicial do web app em um dashboard operacional por perfil, alinhado à jornada já implementada no backend:

```text
solicitação → elegibilidade humana → encaminhamento → viabilidade FTTH → instalação → ativação → serviço ativo
```

A missão não cria novas regras de negócio nem substitui endpoints. Ela prepara a camada visual e o contrato de leitura para o painel operacional, mantendo separação entre dado demonstrativo, dado operacional e produção.

## Escopo implementado

- Dashboard por persona operacional:
  - superadmin/admin;
  - gestão municipal;
  - provedor;
  - auditoria;
  - suporte.
- Modelo tipado em `apps/web/lib/operational-dashboard.ts`.
- Tela principal `apps/web/app/page.tsx` consumindo sessão real via BFF `/api/auth/me`.
- KPIs e filas variando conforme papéis da sessão.
- Esteira operacional compatível com os módulos implementados até a Missão 1.6.
- Avisos explícitos de privacidade e limitação por perfil.
- Layout responsivo com identidade GovTech já aprovada.

## Fora de escopo nesta missão

- Conectar o dashboard a consultas agregadas reais no backend.
- Criar tabelas ou migrations novas.
- Criar relatórios oficiais.
- Criar exportação PDF/CSV.
- Criar notificações transacionais.
- Criar DMS/evidências.
- Exibir CPF bruto, documento sensível, portas internas, topologia do provedor ou dados de outro tenant.

## Regras permanentes

1. Dashboard é leitura operacional, não motor de decisão.
2. Nenhum card pode aprovar, reprovar, suspender ou cancelar benefício automaticamente.
3. IA não decide elegibilidade, pagamento, suspensão, priorização obrigatória ou autorização administrativa.
4. Município vê resumo minimizado de provedor.
5. Provedor vê apenas sua própria fila.
6. Auditoria vê rastreabilidade e conformidade, não dados sensíveis desnecessários.
7. Suporte atua com mínimo privilégio.
8. Qualquer dado demonstrativo precisa estar rotulado até haver endpoint real.

## Critérios de aceite

- Build do web app precisa continuar verde.
- Typecheck precisa continuar verde.
- CI e Security Gate precisam passar antes do merge.
- Tela deve continuar protegida por sessão via middleware/BFF existente.
- O dashboard deve renderizar sem depender de endpoints ainda inexistentes.
- Textos devem deixar claro que os números são referência operacional até a conexão com agregações reais.

## Próximo passo natural

A próxima missão recomendada é criar agregações de leitura no backend para alimentar esse dashboard sem expor dados sensíveis:

- `/dashboard/municipal/summary`;
- `/dashboard/provider/summary`;
- `/dashboard/audit/summary`;
- DTOs minimizados por perfil;
- testes de escopo tenant/organização;
- cache curto e invalidável, se necessário.
