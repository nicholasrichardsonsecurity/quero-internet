# Missão 1.7 — Contratos de API, Erros e Versionamento

## Objetivo

Padronizar a superfície HTTP interna da API para reduzir ambiguidade entre web, integrações futuras, workers e consumidores administrativos.

Esta missão não cria API pública externa nem libera piloto. Ela estabelece um contrato mínimo de resposta, erro, versionamento e documentação técnica para as rotas já existentes.

## Por que esta missão vem agora

O MVP já possui uma trilha operacional inicial:

```text
beneficiário → solicitação → elegibilidade → encaminhamento → viabilidade FTTH → instalação → ativação → serviço ativo
```

Antes de avançar para dashboards reais, notificações, documentos ou integrações IXC/SGP, a API precisa de uma base previsível para:

- tratamento uniforme de erro no frontend;
- rastreabilidade por requisição;
- evolução sem quebra silenciosa;
- documentação de DTOs e status;
- compatibilidade futura com BFF, mobile/PWA e integrações supervisionadas.

## Escopo implementado nesta missão

### 1. Envelope de erro

Todo erro HTTP tratado pela API deve seguir formato estável:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Recurso não encontrado.",
    "statusCode": 404,
    "path": "/rota",
    "timestamp": "2026-09-01T00:00:00.000Z",
    "requestId": "opcional"
  }
}
```

Regras:

- não expor stack trace;
- não expor exception crua;
- preservar mensagem de domínio quando ela já for segura;
- normalizar erros genéricos em mensagem operacional segura;
- incluir `requestId` quando vier em `x-request-id`.

### 2. Códigos de erro estáveis

A primeira versão define códigos estáveis por status HTTP:

| HTTP | Código |
|---|---|
| 400 | `BAD_REQUEST` |
| 401 | `UNAUTHORIZED` |
| 403 | `FORBIDDEN` |
| 404 | `RESOURCE_NOT_FOUND` |
| 409 | `CONFLICT` |
| 429 | `RATE_LIMITED` |
| 500+ | `INTERNAL_ERROR` |

Códigos mais específicos poderão ser adicionados por contexto quando houver necessidade real e testes correspondentes.

### 3. Versionamento inicial

A API continua sem prefixo `/v1` para evitar quebra prematura das rotas do MVP, mas passa a documentar:

- versão contratual atual: `v1`;
- data-base do contrato: `2026-09-01`;
- header recomendado para consumidores internos: `x-api-version`;
- política: mudanças incompatíveis exigem novo contrato ou compatibilidade transitória.

### 4. Documento de contrato

Criado documento consolidado em `docs/architecture/API-CONTRACTS.md` com:

- princípios de contrato;
- envelope de erro;
- versionamento;
- regras de DTO;
- privacidade nos DTOs;
- status conhecidos da jornada;
- política para futuras integrações.

## Fora do escopo

- OpenAPI completo gerado automaticamente.
- SDK externo.
- API pública comercial.
- Integração real IXC/SGP.
- Mudança de todas as rotas para `/v1`.
- Paginação/cursor em todas as listagens.
- Envelope obrigatório para respostas de sucesso.

## Critérios de aceite

- Erros HTTP possuem envelope único e testado.
- Erros 5xx não vazam detalhe interno.
- `x-request-id` é refletido no envelope quando fornecido.
- Documentação diferencia contrato interno, API pública futura e integração externa.
- CI e Security Gate passam antes do merge.
